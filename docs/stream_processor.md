# StreamForge Stream Processor

## Pipeline

```text
Confluent telemetry producer → Kafka → Python consumer group → FastAPI/RocksDB
                                    └→ Bytewax event-time windows → window topic
```

The canonical event contains only the truck ID, temperature, and timezone-aware
event timestamp:

```json
{
  "truck_id": "TRUCK-00001",
  "temperature": 25.5,
  "timestamp": "2026-10-03T12:00:00Z"
}
```

`device_id` is accepted by the Kafka consumer for backwards compatibility and
normalized to `truck_id` before ingestion. Humidity is optional legacy input;
it is not generated by the producer, forwarded to the API, or shown by the
dashboard.

## Processing behavior

The Kafka worker validates the identifier, numeric temperature, and timestamp.
Temperatures outside `-50°C` to `100°C` are rejected; valid temperatures at or
below `0°C` are filtered and acknowledged without entering state. Positive
readings are posted to FastAPI, where the RocksDB store maintains an event-time
five-minute rolling average per truck.

The Bytewax path applies the same positive-temperature filter, keys the stream
by truck, uses a five-minute sliding window with a ten-second event-time
lateness allowance, and publishes results to `streamforge-windowed`.

Workers share the `streamforge-workers` consumer group. Kafka assigns partitions
among active workers. Offsets are committed after backend processing and a
successful changelog flush. Failed backend requests are retried from Kafka;
RocksDB event IDs make redelivery idempotent. At API startup, retained accepted
events in `streamforge-state-changelog` are replayed up to the startup offset
snapshot to rebuild missing state. If Kafka is unavailable, the API continues
with the local RocksDB database.

## Run locally

From the repository root, start Kafka and topic initialization:

```powershell
docker compose -f docker/compose.yaml up -d kafka kafka-init
```

Start the API, then one or more workers in separate terminals:

```powershell
python -m uvicorn streamforge.main:app --host 127.0.0.1 --port 8000
```

```powershell
$env:STREAMFORGE_WORKER_ID="worker-1"
python -m stream_processor.consumer
```

Start the producer in another terminal:

```powershell
python -m producer.telemetry_producer
```

The producer cycles through 50,000 truck IDs at a configurable nominal rate
of 5,000 events per second, corresponding to one reading per truck every ten
seconds. This is a workload configuration, not a benchmark result.

To run the Bytewax dataflow with 20 workers:

```powershell
python -m bytewax.run stream_processor.bytewax_flow:flow -w 20
```

## Metrics and recovery

The API exports Prometheus metrics at `/metrics`, including processed and
filtered event counters, events per second, processing duration, event-time lag,
active workers, and assigned partitions. `/workers` and `/topology` expose
current assignments for the React Flow UI.

The `scripts/throughput_benchmark.py --events 100000` command measures Kafka
producer delivery throughput. Report its measured result; do not treat the
100,000 events/sec target as a guaranteed result. Use
`docs/distributed-review.md` for the worker-failure demonstration procedure.
